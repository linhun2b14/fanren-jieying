## ★ 时机差异清单（这是需要你过目的部分）

搬家时为了**保证零行为差异**，所有效果的时机窗口都取了保守值（对战类统一 `combatStart`）。
但卡文里写明了更细的窗口，引擎的 `satisfiedWindows()` 已经能精确判定。下面是**开着校验之后**会发生的变化：

| 卡 | 现在能打 | 改完能打 | 卡文依据 |
|---|---|---|---|
| 【青竹蜂云剑】【黑血刀】【凌玉灵】【青元剑诀·炼气档】 | 对战刚开始、**双方都没投骰**时 | **轮到我投骰之前**（攻方在准备阶段；应战方在攻方投完后、自己投之前） | 「在对战中投掷骰子前使用」 |
| 【青元剑诀·筑基档】 | 对战刚开始时 | **我投完骰之后** | 「在对战中投掷骰子后使用」 |
| 【寒冰珠】 | 对战刚开始时 | **对方还没投骰之前** | 「对方投掷骰子前使用」 |
| 【颠倒五行阵】 | 对战刚开始时 | **对方投完骰之后** | 「对方投掷骰子后使用」 |
| 【天星大阵】 | 自己回合行动阶段**随时可打** | **只在平局窗口** | 「在对战平局时使用」 |
| 【遮天钟】 | **只能在对战里打** | **任意回合都能打** | 「在任意回合使用」 |
| 【阴魂丝】 | **自己回合也能乱打** | 只在对战开始前 | 「在对方的对战阶段前使用」 |

其中 **2 处是修 bug**（实测复现过）：
- **【天星大阵】平局窗口里根本打不出来** —— `TIE_KINDS` 漏了 `heal`
- **【颠倒五行阵】对方还没投骰就能打** —— 引擎只区分 `pre`/`roll_defender`，没有"谁投了骰"的概念

## ★ 实施中发现并修掉的 3 个真 bug（与重构本身无关，是顺带挖出来的）

## 1. 现状到底哪里疼（都有证据）

### 痛点 A · 触发时机散成 8 个槽 + 6 个扫描函数

`cards.json` 里一张同行者效果被拆到不同字段：

```
onPlace  onTurn  onCombat  onCombat2  onHurt  onLowHp  onWin  onPromote
```

`engine.js` 里有 **6 个各自独立的函数**分别去读它们：

| 行号 | 函数 | 读哪些槽 | 还读**别的牌**吗 |
|---|---|---|---|
| L151 | `passives` | `onTurn` + `onPromote` | 也读装备 |
| L180 | `companionCombat` | `onCombat` + `onCombat2` | 只读同行者 |
| L252 | `hurtMana` | `onHurt` | 只读同行者 |
| L264 | `lowHpRescue` | `onLowHp` | 只读同行者 |
| L274 | `afterCombatMana` | `onCombat` + `onCombat2` | 只读同行者 |
| L286 | `noCombatHeal` | `onTurn` | 只读同行者 |
| L1724 | `runOnWinEffects` | `onWin`（**又是一套字段名**：`mana/draw_qi/steal_equip`） | 也读装备 |

⚠️ 注意 `onWin` / `onPlace` / `onLowHp` 用的是**裸字段**（`{mana:1, draw_qi:1}`），
而 `onTurn`/`onCombat`/`onHurt`/`onPromote` 用 `{kind, value}` —— **同一份文件里两套写法**。

`onPlace` 更糟：它没有扫描函数，**直接内联在 `doPlay` 里**（L1310 附近）。

→ **结论：加一个新的"时机"必须改引擎；加卡必须想清楚该塞哪个槽。**

### 痛点 B · 条件没有求值层，一个组合 = 一个 kind

现在卡池里有 **6 个"条件型 kind"**，每个都是把「动作 + 条件」焊死在一起：

```
combat_bonus_if_hp_le              combat_bonus + 生命≤N
combat_bonus_if_hp_ge              combat_bonus + 生命≥N
combat_bonus_if_enemy_higher_realm combat_bonus + 对方境界更高
combat_bonus_if_companion          combat_bonus + 某同行者在场
damage_higher_realm                damage_target + 目标境界更高
versus_realm_effect                (按对方境界分两个分支)
```

这是**组合爆炸**：再来一张「生命≤3 **且**对方境界更高时 +1」，
只能在上面再加第七个 kind，再改一遍引擎 + 3 个 Set + 前端词典。

### 痛点 C · 元数据散在 4 个地方，靠人记得同步

| 位置 | 内容 | 漏了会怎样 |
|---|---|---|
| `engine.js` L51 `COMBAT_KINDS` | 哪些牌能在对战出牌阶段打 | **已经漏过一次**：【火弹术】的 `win_steal_treasure` 没登记 → 对战里打不出来 |
| `engine.js` L57 `TIE_KINDS` | 哪些牌能改判平局 | 平局时打不出来 |
| `engine.js` L61 `NEEDS_TARGET` | 哪些牌必须先选目标 | 牌被白白消耗、效果落空 |
| `public/app.js` | 60 条 `KIND_TXT` 中文词典 | 新卡在界面上显示英文 id |

### 痛点 D · 每次都要人工跑胜率

加一张纯展示/纯文本的卡也跑 72 局模拟，没必要。

## 2. 新数据格式（完整规格）

### 2.1 卡牌结构

```jsonc
{
  "id": "k_...", "name": "蛮胡子", "type": "companion",
  "realm": 0, "count": 2, "slots": 1, "cat": "修士",
  "text": "●若【生命值】≥4点，在对战时，【战力值】+1。●若【生命值】≤3点，在对战时，【战力值】+1。",

  // ★ 唯一的改动：所有触发效果统一进这一个数组
  "effects": [
    { "when": "combat", "op": "combat_bonus", "value": 1, "if": { "hp": { "gte": 4 } } },
    { "when": "combat", "op": "combat_bonus", "value": 1, "if": { "hp": { "lte": 3 } } }
  ],

  // 卡牌属性（不是"触发效果"），保持顶层
  "absorb": 1, "cardCostDiscount": 1, "equipCost": 5
}
```

### 2.2 `when` —— 触发时机（v2 修订：按你的要求细化对战子窗口）

原方案把对战统统塞进一个 `combat`，**太粗了**。卡文里其实有明确的子窗口，
而且现在**因为子窗口不存在，已经出了真 bug**（见 §2.5）。

改完分两类。**A 类是"出牌窗口"**（决定你什么时候能点这张牌），
**B 类是"自动触发点"**（不用点，到点自己生效）。

#### A · 出牌窗口

| `when` | 含义（卡文原话） | 卡池里谁在用 |
|---|---|---|
| `play` | 自己的回合使用（无对战） | 青蛟旗、撼地符… |
| `place` | 首次放置此【同行者】 | 血玉蜘蛛、铁火蚁、离龟 |
| `combatStart` | 在对战中**出牌阶段**（双方都还没投骰） | 金光砖符、虚天鼎、敛气术、青火雷 |
| `beforeMyRoll` | **我方**投掷骰子**前** | 黑血刀、青竹蜂云剑、凌玉灵、青元剑诀(炼气档) |
| `afterMyRoll` | **我方**投掷骰子**后** | 青元剑诀(筑基档) |
| `beforeFoeRoll` | **对方**投掷骰子**前** | 寒冰珠 |
| `afterFoeRoll` | **对方**投掷骰子**后** | 颠倒五行阵 |
| `tie` | 对战**平局**时（双方各限一张） | 天星大阵 |

> 这四个「投骰前/后」就是你要的。引擎里能精确判定：
> 记录 `combat.rolled[玩家id]`，则
> `beforeMyRoll` = 我没投 / `afterMyRoll` = 我投了 /
> `beforeFoeRoll` = 对方没投 / `afterFoeRoll` = 对方投了。

#### B · 自动触发点（不用点牌）

| `when` | 含义 | 卡池里谁在用 |
|---|---|---|
| `turn` | 自己回合开始 | 韩立、三目豹 |
| `passive` | 常驻数值（只被汇总读） | 慕沛灵、紫灵、玄骨 |
| `win` | 对战**获胜** | 绿煌剑、风云幡、寒蛟、韩立、三目豹、宋玉、火龙童子、噬金虫、王蝉、青火雷 |
| `lose` | 对战**失败** | 风雷翅、踏云靴、透明丝线、青火雷 |
| `afterCombat` | 对战结算**之后** | 凌玉灵 |
| `hurt` | 本人受到伤害 | 燕如嫣、慕沛灵 |
| `lowHp` | 生命值濒危 | 元瑶 |
| `promote` | 晋升时 | 辛如音、玄骨、文思月 |

> **关于 `lose` 有一个规则分叉要你拍板**，见 §8.6。
> 现在【踏云靴】【透明丝线】【风雷翅】是**提前声明**（在投骰前打出去，赌一把，输了才生效）；
> 卡文写的是「在对战失败时使用」，严格按卡文应该是**看到败局已定之后再打出**。
> 两种做法对牌力和手感影响很大，所以单独列出来问。

### 2.5 因为缺少子窗口，现在已经存在的两个真 bug

| # | 卡 | 卡文 | 现在的实际行为 | 根因 |
|---|---|---|---|---|
| 1 | **【天星大阵】** | 「在对战**平局**时使用，恢复1点生命值」 | **平局窗口里根本打不出来**，报「平局阶段只能打出改变战力结果的卡牌」 | `TIE_KINDS` 集合里漏了 `heal`（和之前【火弹术】漏登记 `COMBAT_KINDS` 是同一类错，靠人工维护集合必然再犯） |
| 2 | **【颠倒五行阵】** | 「在对战中**对方投掷骰子后**使用，强制对方重新投掷」 | **对方骰子还没投就能打出来**（`stage=pre` 就放行） | 引擎只区分 `pre`/`roll_defender` 两个阶段，没有"谁投了骰"的概念 |

> 这两条我都实测复现了。
> 有了 `when` 子窗口 + 元数据派生，**这类 bug 从结构上不可能再出现**
> —— 牌能不能打，由它的 `when` 和当前窗口判定，不再靠人往集合里补名字。
>
> ⚠️ 但请注意副作用：**修 bug 意味着行为会变**（以前能乱打的牌之后不能乱打了）。
> 所以下面 §8.5 要你选「纯搬家」还是「搬家+开校验」。

### 2.6 `tiers` 一起迁（按你的选择）

法术类装备的多境界档位，现在长这样：

```json
"tiers": [
  { "realm": 1, "text": "炼气期：…骰子点数+1", "effect": { "kind": "dice_bonus", "value": 1, "cap": 6 } },
  { "realm": 2, "text": "筑基期：…额外投掷1次骰子", "effect": { "kind": "reroll_dice", "value": 1 } },
  { "realm": 3, "text": "结丹期：…战力值+1", "effect": { "kind": "combat_bonus", "value": 1 } }
]
```

改完（内层 `effect` 也变成 `effects` 数组，与卡牌主体一致）：

```json
"tiers": [
  { "realm": 1, "text": "炼气期：…骰子点数+1",
    "effects": [ { "when": "beforeMyRoll", "op": "dice_bonus", "value": 1, "cap": 6 } ] },
  { "realm": 2, "text": "筑基期：…额外投掷1次骰子",
    "effects": [ { "when": "afterMyRoll", "op": "reroll_dice", "value": 1 } ] },
  { "realm": 3, "text": "结丹期：…战力值+1",
    "effects": [ { "when": "combatStart", "op": "combat_bonus", "value": 1 } ] }
]
```

顺带把三档的 `when` **按卡文精确分开**——这正是卡文写的
（炼气档"投骰前"、筑基档"投骰后"、结丹档"出牌阶段"），
现在它们全都被当成同一个 `combat`，所以三档在时机上没区别。

### 2.3 `if` —— 条件谓词（这次重构的核心，消灭组合爆炸）

`if` 是一个对象，多个键之间是 **AND**。所有键都可选。

```jsonc
"if": {
  "hp":         { "lte": 3, "gte": 4, "lt": 5, "gt": 0, "eq": 6 },  // 自己的生命值
  "realm":      { "lte": 2, "gte": 1, "eq": 3 },                    // 自己的境界
  "enemyRealm": { "higher": true, "lower": true, "lte": 2, "gte": 3 }, // 当前对战对手的境界
  "target":     { "realmHigher": true, "realm": { "gte": 3 }, "notSelf": true }, // 被指定的目标
  "companion":  "离龟",          // 场上（自己）有这张同行者
  "hasEquip":   true,           // 储物袋里有装备类宝物牌（【银月】需要）
  "inCombat":   true,           // 必须有进行中的对战
  "turnFlag":   { "combat": false } // 本回合是否已发起过对战（【墨彩环】需要）
}
```

有了这一层，前面那 6 个"条件型 kind" **全部消失**：

| 老 kind | 新写法 |
|---|---|
| `combat_bonus_if_hp_le` | `op: combat_bonus` + `if: {hp:{lte:N}}` |
| `combat_bonus_if_hp_ge` | `op: combat_bonus` + `if: {hp:{gte:N}}` |
| `combat_bonus_if_enemy_higher_realm` | `op: combat_bonus` + `if: {enemyRealm:{higher:true}}` |
| `combat_bonus_if_companion` | `op: combat_bonus` + `if: {companion:'离龟'}` |
| `damage_higher_realm` | `op: damage_target` + `if: {target:{realmHigher:true}}` |
| `versus_realm_effect`（天雷子） | 两条：`op:win_extra_damage if:{enemyRealm:{lte:2}}` + `op:dice_bonus if:{enemyRealm:{gte:3}}` |

> `versus_realm_effect` 是最好的例子：它现在是把两种效果塞进**一个 kind 的四个参数**
> （`lowRealm/onWinDamage/highRealm/diceBonus`），改完就是两条自解释的数据。

### 2.4 `op` + 参数

`op` 就是现在的 `kind`（英文 id 不动，避免全库重命名）。
每个 `op` 的中文标签、能否对战用、能否改判平局、是否必须选目标 —— 全部登记在**一张表**里。

```js
// server/effect-meta.js —— 单一来源
export const OPS = {
  combat_bonus:  { label: '对战战力+',   timing: 'combat', tie: true },
  damage_target: { label: '指定目标受伤', timing: 'play', needsTarget: true },
  damage_attacker:{label: '让发起对战者受伤', timing: 'combat', requiresCombat: true },
  mana_regen_bonus:{label:'每回合法力恢复+', passive: true },
  // ... 共 60 条
};
```

`COMBAT_KINDS` / `TIE_KINDS` / `NEEDS_TARGET` / 前端词典 **全部由这张表派生**：

```js
const COMBAT_KINDS = new Set(opsWhere(o => o.timing === 'combat'));
const TIE_KINDS    = new Set(opsWhere(o => o.tie));
const NEEDS_TARGET = new Set(opsWhere(o => o.needsTarget));
```
→ 从"4 处要同步"变成"1 处定义，3 处自动生成，前端自动下发"。

## 3. 真实卡逐张对照（这是你验收的重点）

### 3.1 【蛮胡子】—— 现在被迫用了 `onCombat2` 补丁

**现在**
```json
"onCombat":  { "kind": "combat_bonus_if_hp_ge", "value": 1, "threshold": 4 },
"onCombat2": { "kind": "combat_bonus_if_hp_le", "value": 1, "threshold": 3 }
```
`onCombat2` 是**今天才为它加的字段**，而且 `companionCombat` 得写 `[def.onCombat, def.onCombat2]` 硬编码两槽。

**改完**
```json
"effects": [
  { "when": "combat", "op": "combat_bonus", "value": 1, "if": { "hp": { "gte": 4 } } },
  { "when": "combat", "op": "combat_bonus", "value": 1, "if": { "hp": { "lte": 3 } } }
]
```
`onCombat2` 字段**消失**，想加第三条也不用再改引擎。

### 3.2 【凌玉灵】—— 两条不同时机的效果

**现在**
```json
"onCombat":  { "kind": "dice_bonus", "value": 1, "cap": 6 },
"onCombat2": { "kind": "after_combat_mana", "value": 1 }
```
（第二条明明是"对战**结束后**"，却塞在 `onCombat`）

**改完**
```json
"effects": [
  { "when": "combat",      "op": "dice_bonus",        "value": 1, "cap": 6 },
  { "when": "afterCombat", "op": "after_combat_mana", "value": 1 }
]
```

### 3.3 【天雷子】—— 现在一个 kind 塞四个参数

**现在**
```json
"effect": { "kind": "versus_realm_effect", "lowRealm": 2, "onWinDamage": 1, "highRealm": 3, "diceBonus": 1 }
```

**改完**
```json
"effects": [
  { "when": "play", "op": "win_extra_damage", "value": 1, "if": { "enemyRealm": { "lte": 2 } } },
  { "when": "play", "op": "dice_bonus",       "value": 1, "if": { "enemyRealm": { "gte": 3 } } }
]
```
自解释，且**改条件不用碰引擎**。

### 3.4 【血玉蜘蛛】—— 三个不同时机

**现在**
```json
"onPlace": { "draw_treasure": 3 },       ← 裸字段
"onWin":   { "mana": 2 }                 ← 又是另一套裸字段
```

**改完**
```json
"effects": [
  { "when": "place", "op": "draw_treasure", "value": 3 },
  { "when": "win",   "op": "mana",          "value": 2 }
]
```

### 3.5 【元瑶】—— 濒危自救

**现在**
```json
"onLowHp": { "threshold": 1, "heal": 2, "discardSelf": true }
```
（`threshold` 其实是条件，被塞进了效果参数里）

**改完**
```json
"effects": [
  { "when": "lowHp", "op": "heal_and_discard", "value": 2, "if": { "hp": { "lte": 1 } } }
]
```

### 3.6 【银月】—— **这条现在做不到，改完就能做**

卡文：「当【储物袋】中有任意【装备类宝物牌】，在对战时，可额外投掷1次骰子，取最大值。」

**现在**：`{ "kind": "reroll_dice", "value": 1 }` —— **条件根本没实现**，
不管储物袋里有没有装备，都白送额外掷骰。所以它现在还挂在"未实装"清单里。

**改完**
```json
{ "when": "combat", "op": "reroll_dice", "value": 1, "if": { "hasEquip": true } }
```
→ 从"未实装"变成"已实装"，**且没改一行引擎**。这就是条件求值层的价值。

### 3.7 为什么 `absorb` / `slots` / `cardCostDiscount` **不进** `effects`

它们是**卡牌固有属性**（占几个放置位、替挡几次、法耗减多少），
不是"某时点触发的动作"，而且被"放置位计算""受伤路径""费用计算"直接当属性读。
塞进 `effects` 反而要绕一圈。**保持顶层**，但会在元数据表里登记说明。

#### 8.5 时机校验：纯搬家，还是搬家 + 立即开校验？

细化出 `beforeMyRoll`/`afterFoeRoll` 这些窗口之后，引擎**要不要马上按它拦牌**，是两条路：

| 方案 | 做什么 | 后果 |
|---|---|---|
| **A · 纯搬家** | 只把 `when` 写进数据，引擎暂时**不校验**，谁能打谁不能打**和现在完全一样** | **零行为差异**，风险最低；但 §2.5 那两个 bug 仍在，只是"有了修复的位置" |
| **B · 搬家 + 开校验** | 立即按 `when` 和当前窗口判定能不能打 | **修掉两个真 bug**（天星大阵平局可打、颠倒五行阵不再能提前打）；但**行为会变**，有些牌以前能乱打之后不能 |

**我建议 B，但分两步走**：先按 A 搬完并让 15 个测试全绿（证明"搬家本身没改行为"），
然后加一个开关跑一遍「老行为 vs 新行为差异清单」给你看——列出**具体哪几张牌在什么情况下从"能打"变成"不能打"**，
你确认没问题再开启校验（B）。这样风险可控，且你能看到每一处变化。

#### 8.6 【对战失败时使用】：提前声明，还是真的"输了再打"？

卡文：**风雷翅**「在对战失败时，投掷1次骰子，点数为1、3、6，不受本次对战失败的惩罚」、
**踏云靴**「在对战失败时使用，不受本次对战失败的惩罚」、
**透明丝线**「在对战失败时使用，让对方受到1点伤害」。

| 方案 | 机制 | 手感 / 影响 |
|---|---|---|
| **现状 · 提前声明** | 在投骰**前**打出去，记在 `loseSave`/`loseImmunity`/`loseRetaliate`，结算时若真输了才生效 | 你得**赌**，赢了就白扔一张牌。这三张现在偏弱 |
| **按卡文 · 失败窗口** | 结算出结果后、扣血前，**输家**可以打出这类牌翻盘 | 严格贴卡文，这三张**明显变强**（不再浪费）；但需要引擎新增一个"失败窗口"阶段，且会影响平衡 |

这一条会影响牌力，**不是纯技术选择**，得你定。如果要"失败窗口"，
我会额外加一个 `when: 'lose'` 的**出牌窗口**（不是自动触发），并把它和 §8.5 的校验一起做。
